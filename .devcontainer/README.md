# Dev container

A ready-to-use build environment for telaio: JDK 25, Maven, and a real Docker daemon for the Testcontainers suites. The
image is pulled, never built locally.

## Prerequisites

Nothing but Docker plus an IDE client.

| Host    | Requirement                                                |
|---------|------------------------------------------------------------|
| Windows | Docker Desktop in **Linux container** mode (WSL 2 backend) |
| Linux   | Docker Engine (or Docker Desktop)                          |

The image is `linux/amd64` only.

## Opening it

`devcontainer.json` is an open specification and `customizations` is namespaced per tool, so the same file serves every
client:

- **IntelliJ IDEA** — open `devcontainer.json` in the editor, then use the *Create Dev Container* gutter icon → **Create
  Dev Container and Mount Sources…** (the *Clone Sources* variant clones from a remote instead, losing uncommitted
  work). Progress shows in the *Services* tool window; then *Connect* — the first connection downloads the backend IDE,
  so it is the slow one. The backend then runs as a JVM inside the container; the client is a frame of your local IDE,
  not a separate application, so closing the local IDE ends the session while the container keeps running.
- **VS Code** — the *Dev Containers* extension → *Reopen in Container*.
- **CLI** — no IDE needed:

  ```bash
  npx --yes @devcontainers/cli up --workspace-folder .
  npx @devcontainers/cli exec --workspace-folder . bash -lc 'mvn -B clean verify'
  ```

## What is inside

`ghcr.io/marcopag90/java-maven-devcontainer:jdk25-v1` — Ubuntu 24.04, Temurin JDK 25, Maven 3.9.15, git, gh, perl,
gnupg, jq, zip. The tag is pinned on purpose: moving to a newer base is a deliberate decision, not a side effect of a
rebuild.

JDK 25 is what the full reactor requires: `telaio-showcase` targets Java 25, and the enforcer's build-JDK floor follows
each module's target (`requireJavaVersion [${maven.compiler.release},)`). The library modules build with JDK 21+ and
emit Java 21 bytecode via `--release 21`.

`devcontainer-lock.json` pins the resolved digest of the `docker-in-docker` feature, whose reference (`:4`) is otherwise
a floating major. It is committed for the same reason the image tag is pinned, and it is regenerated by the client — to
take a newer feature release, delete it and bring the container up again.

## Docker-in-Docker, not the host socket

The `docker-in-docker` feature gives the container its own daemon rather than sharing the host's. That is deliberate:
inside the container `localhost` must really be localhost, so
`telaio-showcase/compose.yaml` works unmodified and `@ServiceConnection` wires the datasource with no override. With the
host socket, a container published on the host's `localhost:5432` would not be reachable that way.

## Volumes

| Volume             | Mount                | Why                                                                                                                                                                                                                 |
|--------------------|----------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `telaio-dind`      | `/var/lib/docker`    | The inner daemon's image store. The Testcontainers vendor matrix pulls ~6 GB (Oracle XE and SQL Server dominate); without this they are re-pulled on every recreate.                                                |
| `telaio-m2`        | `~/.m2`              | Maven repository.                                                                                                                                                                                                   |
| `telaio-jetbrains` | `~/.cache/JetBrains` | Caches and indexes of the JetBrains backend. Not the backend itself — that is deployed under `/tmp`, outside our control. What this saves is re-indexing all the modules of the reactor build after every recreate. |
| `telaio-gh`        | `~/.config/gh`       | Keeps the `gh` login across recreates.                                                                                                                                                                              |

Deleting a volume is safe — it only costs a re-download. `post-create.sh` hands the fresh (root-owned)
volumes to the container user on first create.

The `docker-in-docker` feature (v4+) also mounts its own volume, `dind-var-lib-containerd-${devcontainerId}`, at
`/var/lib/containerd` — not listed above because we don't name or control it (the feature declares it as a default
mount; `devcontainerId` is stable per workspace, so it persists across ordinary recreates same as the volumes above).
It matters because the current Docker Engine stores actual pulled-image content (the vendor matrix layers) under
`/var/lib/containerd`, not `/var/lib/docker` — `telaio-dind` mostly holds daemon bookkeeping. Before v4, that
containerd state had nowhere persistent to live and was silently wiped on every container recreate, defeating
`telaio-dind`'s caching purpose for the actual image bytes; v4's added mount is what makes the cache real. One
consequence: deleting `telaio-dind` alone no longer forces a clean image cache — find the matching
`dind-var-lib-containerd-*` volume too (`docker volume ls`) if you want to reclaim that space or force a full re-pull.

## Notes

- **Windows I/O.** The workspace is a bind mount through the host filesystem, so Maven is measurably slower than on a
  Linux host. The first `mvn clean verify` also pulls ~6 GB of database images; after that the `docker-in-docker`
  feature's volumes (see [Volumes](#volumes)) keep them, so later recreates don't re-pull.
- **User and file ownership.** The image declares `remoteUser: vscode`, and `updateRemoteUserUID`
  (the default for `image`-based containers) remaps that user onto the host uid on Linux.
  `post-create.sh` registers the workspace as a git `safe.directory` as a backstop.
- **Signed releases are not supported in here.** No GPG key is mounted; signing happens in CI (`publish.yml`,
  `-Dgpg.signer=bc`). Use the container for building and testing.
- **`portsAttributes` is honored unevenly.** The JetBrains documentation states that only `label` is supported. In
  practice IDEA does keep the rest in its container model, but treat `onAutoForward` as reliable on VS Code and the
  `devcontainer` CLI only. Nothing breaks either way.
- **One container at a time.** Each client creates its own container, and they all mount `telaio-dind` at
  `/var/lib/docker` (plus, since `devcontainerId` is derived from the workspace path rather than the client, the same
  `dind-var-lib-containerd-*` volume at `/var/lib/containerd`) — two inner daemons over the same storage directories
  contend for the same locks. Remove the previous container before opening the project with a different client. The
  label to filter on depends on who created it:

  ```bash
  # devcontainer CLI and VS Code — lowercased drive letter, backslashes
  docker rm -f $(docker ps -aq --filter 'label=devcontainer.local_folder=d:\path\to\telaio')

  # IntelliJ IDEA — original case, forward slashes
  docker rm -f $(docker ps -aq --filter 'label=com.intellij.devcontainer.sources.path=D:/path/to/telaio')
  ```

  `docker ps -a` and picking the id by hand works just as well.
- The image is maintained at <https://github.com/marcopag90/java-maven-devcontainer>. It is deliberately generic — no
  editor, no agent, no personal configuration — so project-specific tooling belongs in this file, not in the image.
